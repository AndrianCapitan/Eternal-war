# Z-уровни для Space Station 14: поэтапный план работы с Claude Code

> Версия от 27.10.2026. Имена существующих классов, файлов и событий — ориентир по upstream (space-wizards) на осень 2026. В вашем форке они могут отличаться, поэтому этап 0 начинается со сверки, а Claude проверяет каждое имя по коду, а не берёт его из этого файла на веру. Новые компоненты и системы, которые предстоит написать (`ZStackComponent` и т. п.), названы условно.

## Как пользоваться файлом

1. Скопируйте `PLAN.md` и `PROGRESS.md` в свой форк, в папку `docs/zlevels/`.
2. Добавьте в корневой `CLAUDE.md` блок из приложения А.
3. Идите по этапам по порядку. Один этап — одна или несколько сессий Claude Code. Каждая сессия начинается с промпта этапа (он есть в конце каждого этапа; общий шаблон — приложение Б).
4. В конце этапа Claude обновляет `PROGRESS.md` и `DECISIONS.md`. Тогда следующая сессия начинает не с нуля, а с записанных выводов.
5. Claude не обязан читать весь план: ему достаточно разделов 2–4 и раздела своего этапа (ищется по заголовку «### Этап N»).

## 2. Целевая архитектура

### 2.1 Ключевые решения (на этапе 1 оформляются как ADR в `DECISIONS.md`)

| # | Решение | Почему | Отвергнутая альтернатива |
|---|---|---|---|
| Р1 | Уровень = отдельная карта (сущность карты + `MapId`) | У каждой карты свой физический мир и свой поиск сущностей, а проверка дальности взаимодействия не проходит между картами. Значит, по умолчанию между уровнями ничего не «протекает» | Одна карта + Z-координата у сущностей: пришлось бы фильтровать физику, поиск, взаимодействия и тайлы почти во всей игре. Нативный Z в движке — переписывание движка |
| Р2 | Глубина — целое число: 0 — основной уровень станции, отрицательные — ниже, положительные — выше | Просто, совместимо с уровнями под станцией (шахты) | — |
| Р3 | Стек описывается реестром (сущность в nullspace, отправляется клиентам) и компонентом на каждой карте уровня. Ссылки — `EntityUid` карт (в сети — `NetEntity`), не `MapId` | Сущность — каноничная ссылка и передаётся по сети | Хранить `MapId` |
| Р4 | Единая система координат: точка (x, y) на всех уровнях — одна вертикаль. Гриды станции на всех уровнях выровнены (одинаковые мировые позиция и поворот) и неподвижны | Переход между уровнями — это смена карты при тех же XY | Хранить смещения между гридами |
| Р5 | Проём — отдельный тайл `OpenSpace` (не космос): прозрачный, держит атмосферу, с него падают | Космос на верхнем уровне и дыра в полу — разные вещи | Использовать пустой тайл |
| Р6 | Переходы: ступени (шагом), стремянка и люк (действие + DoAfter), падение. Позже — лифты и полёт в невесомости | Покрывает основные сценарии | — |
| Р7 | Сеть: на соседних уровнях сервер держит для игрока «наблюдателя» — сущность с `EyeComponent`, подписанную через `ViewSubscriberSystem` | Так уже работают камеры наблюдения. Движок не трогаем | Патч PVS в движке |
| Р8 | Рендер: нижние уровни рисуются дополнительными глазами в контентном вьюпорте и подкладываются под основной мир с затемнением. Глубина ограничена 1–2 уровнями | Возможно без правки движка | Однопроходный рендер нескольких карт в Clyde (патч движка) |
| Р9 | Атмос MVP: вертикальный обмен газом через проёмы как atmos-устройство. Ядро атмоса (LINDA, Monstermos) не трогаем | Надёжно и дёшево | Полный 3D-атмос (опциональный этап B) |
| Р10 | Стояки труб, кабелей и утилизации — узлы с вертикальной связью с парным узлом на соседнем уровне | Сети узлов уже умеют произвольные связи | — |
| Р11 | «Одно место»: хелпер `SameStack(...)` и аудит всех сравнений `MapId`/`GridUid`. Станционные системы считают уровни одной станции одним местом | Иначе радио, гравитация и сети устройств сломаются | — |
| Р12 | Хранение: один файл карты на уровень + компонент конфигурации станции в `GameMapPrototype` со списком уровней. Одноуровневые карты работают без изменений | Совместимо с текущими картами и тестами | Все уровни в одном файле (проверить, поддерживает ли ваш `MapLoaderSystem` несколько карт в файле) |
| Р13 | Движок не меняем до явной точки решения. Если меняем — минимальный патч в форке RobustToolbox, отдельный ADR | Слияния с upstream и так будут болезненными | — |

### 2.2 Черновая модель данных (финализируется на этапе 1)

```
ZStackComponent           — на сущности-реестре в nullspace, сетевой
  Levels: depth -> EntityUid карты (отсортировано), MinDepth, MaxDepth

ZLevelComponent           — на каждой карте уровня, сетевой
  Stack: EntityUid, Depth: int

ZLevelViewerComponent     — на игроке, серверный
  Eyes: depth -> EntityUid наблюдателя

StationZLevelsComponent   — конфигурация станции (задаётся в GameMapPrototype), серверный
  Levels: список (Depth, путь к файлу карты)

Тайл OpenSpace + ZOpenSpaceComponent — служебная сущность на каждом тайле проёма
  (триггер падения на этапе 4, atmos-устройство на этапе 8)

ZTransitComponent         — ступени, стремянки, люки: тип, направление, парная сущность
ZFallBlockerComponent     — маркер «не падать здесь» (решётка, помост, закрытый люк)
Вертикальные узлы: ZPipeNode, ZCableNode; DisposalZTube
```

API `SharedZLevelSystem` (условные имена):

- `TryGetStack(EntityUid map, out Entity<ZStackComponent> stack)`
- `TryGetMapAt(stack, int depth, out EntityUid map)`, `TryGetOffsetMap(EntityUid map, int delta, out EntityUid other)`
- `GetDepth(EntityUid map)`
- `SameStack(EntityUid a, EntityUid b)` — для сущностей и карт
- `TryProject(MapCoordinates from, int delta, out MapCoordinates to)`
- `TryGetTileAt(EntityCoordinates at, int delta, out (EntityUid Grid, TileRef Tile) result)`
- `TryTransfer(EntityUid ent, int delta | EntityUid map, ZTransferOptions options)`

События (по канону SS14: `[ByRefEvent] record struct`):

- `ZLevelTransferAttemptEvent` (с `Cancelled`) и `ZLevelTransferredEvent` (старая карта, новая карта, дельта)
- `ZFallAttemptEvent` и `ZFallLandedEvent` (сколько уровней пролетел)
- `ZStackChangedEvent` (уровень добавлен или удалён)

### 2.3 MVP и не-цели

**MVP — двухпалубная станция работает в реальном раунде:**

- стек из 2–3 уровней грузится из конфигурации карты, гриды всех уровней — члены одной станции;
- есть ступени, стремянка, проём и падение с уроном;
- игрок видит нижний уровень сквозь проём;
- воздух перетекает через проём; газовые трубы, кабели и утилизация проходят между уровнями;
- радио, гравитация, сети устройств и объявления работают на всех уровнях;
- призраки и админы переключают уровни; маппер может редактировать и сохранять все уровни;
- одноуровневые карты работают как прежде; всё выключается одной настройкой (CVar).

**Не входит в MVP:** многопалубные шаттлы, навигация NPC между уровнями, полный 3D-атмос, лифты, бой между уровнями, высота внутри уровня (прыжки, «high ground»).

## 3. Подготовка Claude Code (один раз)

1. Откройте сессию Claude Code в папке форка.
2. Убедитесь руками, что всё работает до Claude: `python RUN_THIS.py`, `dotnet build`, запуск `runserver` и `runclient`.
3. Выполните `/init`, затем допишите в `CLAUDE.md` блок из приложения А.
4. Разрешения. Чтобы не подтверждать каждую команду, разрешите `dotnet build`, `dotnet test` и безопасные команды git. Можно попросить Claude: «сократи запросы разрешений» (скилл `fewer-permission-prompts`).
5. Ветки: `zlevels/main` — интеграционная; на каждый этап — `zlevels/stage-NN-<имя>`; пробы — в отдельном git worktree (`zlevels/probe-*`), чтобы не засорять основную ветку.
6. Изоляция кода (важно для слияний с upstream):
   - новый код — в папках `ZLevels`: `Content.Shared/ZLevels`, `Content.Server/ZLevels`, `Content.Client/ZLevels`, `Resources/Prototypes/ZLevels`, локализация — в отдельных `.ftl`;
   - правки чужих файлов — минимальные, обрамлены комментариями `// ZLevels-start` и `// ZLevels-end`;
   - если в форке уже принята своя схема (например, папки с префиксом форка), следуйте ей.
7. Вложенные `CLAUDE.md`. На этапе 2 Claude создаёт `Content.Shared/ZLevels/CLAUDE.md` с кратким описанием архитектуры. Claude Code подхватывает такие файлы, когда работает в этой папке.

**Золотые правила для Claude** (повторены в приложении А):

- не менять RobustToolbox без явного согласия;
- не копировать код CrystallEdge;
- каждая механика — с интеграционным тестом;
- сначала план в режиме планирования, потом код;
- маленькие коммиты, сборка после каждого шага;
- находки — в `docs/zlevels/notes/`, решения — в `DECISIONS.md`;
- не править файлы карт (`Resources/Maps/*.yml`) массово без запроса.

3. Режим планирования.
4. Промпт этапа.

8. Ручная проверка в игре по чек-листу этапа.
9. `/code-review high` по ветке этапа, исправления.
10. Обновить `PROGRESS.md` и `DECISIONS.md`, слить в `zlevels/main`.

## 5. Этапы

### Этап 0. Разведка и подготовка

**Цель.** Рабочая среда и «карта местности»: записки о том, как устроены нужные части движка и игры, и полный аудит мест, которые сломаются от многоуровневости. Код не пишем.

**Усилия:** high · субагенты Explore для широких поисков · **Ветка:** `zlevels/stage-00-research`

**Задачи**

0.1. **Базовая линия.** Сборка, запуск, `dotnet test Content.Tests`, интеграционные тесты (полный прогон — в фоне, он долгий). Записать в `PROGRESS.md` время сборки и тестов и список тестов, которые падают до любых изменений.

0.2. **Версия движка.** Ревизия подмодуля RobustToolbox; входит ли в неё PR #7067. Если нет — решить, обновлять ли движок: это отдельная задача со своими рисками для форка.

0.3. **Записка `docs/zlevels/notes/engine.md`** — по 1–2 абзаца на тему, с путями к файлам и ключевыми методами:
- карты: создание и удаление, `MapId` против сущности карты, пауза, MapInit;
- гриды: тайлы, чанки, событие смены тайла, движение гридов, обход гридов (как сущность меняет родителя между гридом и картой);
- трансформы: `EntityCoordinates` и `MapCoordinates`, `SetCoordinates`/`SetMapCoordinates`, что происходит при смене карты (физика, суставы, контейнеры);
- физика: физический мир на карту, контакты, пробуждение тел;
- `EntityLookupSystem`: поиск по карте и гриду;
- PVS: как выбирается, что отправить клиенту; `ViewSubscriberSystem` (так работают камеры наблюдения); `PvsOverrideSystem`; бюджеты и CVars;
- рендер клиента: вьюпорты (`IClydeViewport`), `MainViewport`/`ScalingViewport` (это контентный код), оверлеи и `OverlaySpace` (например, `WorldSpaceBelowWorld` — там рисуется параллакс), свет, FOV, шейдеры;
- предсказание и интерполяция (после #7067: render transforms, snap-методы);
- сохранение и загрузка карт (`MapLoaderSystem`), формат файла, как исключить компонент из сохранения.

0.4. **Записка `notes/content.md`:**
- GameTicker: загрузка игровой карты, `GameMapPrototype` (секция `stations` и переопределения компонентов), события после загрузки карты, порядок MapInit на старте раунда;
- станции: `StationSystem`, члены станции, `AddGridToStation`, `StationPostInitEvent`, `GetOwningStation`, выбор «самого большого грида» (по нему стыкуется эвакуация);
- атмос: `GridAtmosphereComponent`, `TileAtmosphere`, `AtmosDirection` (только 4 стороны, Up/Down нет), LINDA, Monstermos, горячие точки, `AtmosDeviceComponent` и событие обновления устройства;
- узлы: `NodeContainer`, `NodeGroupSystem`, как узел находит соседей (метод поиска соседей получает свой грид — вертикальным узлам придётся искать грид соседнего уровня), питание, трубы и их слои (если есть в вашей версии);
- утилизация: как капсула переходит между сегментами;
- гравитация: генератор включает гравитацию у своего родителя, то есть у своего грида. На других уровнях гравитации не будет;
- `ChasmSystem` + `StepTriggerSystem` — готовый образец падения (только Chasm удаляет сущность, а нам нужно её перенести);
- тяга (`PullingSystem`), пристёгивание, суставы, DoAfter, броски;
- радио: `RadioSystem` сравнивает `MapID` отправителя и получателя и ищет сервер телекоммуникаций на той же карте (`HasActiveServer`);
- сети устройств: проводная сеть (`WiredNetworkSystem`) принимает пакет только с того же `GridUid`; беспроводная — по радиусу и карте;
- чат и звук: радиус слышимости, проверка карты;
- взрывы, радиация, ЭМИ;

### Этап 1. Проектирование и технические пробы

**Цель.** Утверждённый `DESIGN.md` и снятые главные риски (рендер и сеть) до основной разработки.

**Задачи**

### Этап 3. Перемещение между уровнями

**Цель.** Одна надёжная функция переноса сущности на другой уровень и два первых способа перехода: стремянка и ступени.

**Усилия:** xhigh · **Зависит от:** 2 · **Ветка:** `zlevels/stage-03-transit`

**Задачи**

3.1. **Функция переноса** `TryTransfer(ent, delta | map, options)`:
- событие-попытка (можно отменить) → проверки → перенос → событие-итог;
- точка назначения — те же XY (или со смещением для ступеней); если под точкой есть грид — родителем становится грид, иначе карта;
- тянущий и тянутый — переносить пару или разрывать связь (по `DESIGN.md`); пристёгнутый — отстегнуть; суставы — снять; активные DoAfter — отменить; брошенный предмет — завершить бросок; ведомые сущности (транспорт, переселение ввода) — по правилу; содержимое контейнеров едет с владельцем само; заякоренные — запрещено;
- скорость — сбросить или сохранить (по `DESIGN.md`);
- проверить, что глаз игрока следует за ним автоматически.

3.2. Заменить телепорт в `zup`/`zdown` на `TryTransfer`.

3.3. **Стремянка:** парные сущности «низ» и «верх» в одной клетке на соседних уровнях; пара находится автоматически по координатам (при MapInit и при постройке). Действие «подняться/спуститься» (альтернативное действие или контекстное меню), DoAfter 1–2 с, звук. Если выход заблокирован стеной или непроходимым объектом — отказ со всплывающим сообщением.

3.4. **Ступени:** направленный объект на нижнем уровне. Шаг на ступени по направлению подъёма переносит на уровень выше на клетку вперёд; на верхнем уровне — «площадка» для спуска. Вход сбоку не срабатывает. Реализация — `StepTrigger` или сенсорная фикстура (выбрано на этапе 1).

3.5. **Предсказание.** На этом этапе перенос только на сервере. Проверить, есть ли рывок на клиенте. Если есть — короткая анимация (опускание или подъём спрайта, затемнение). Смена карты не интерполируется даже после #7067, поэтому анимация — основной способ скрыть телепорт. Предсказанный перенос — отдельной задачей позже.

3.6. **Предзагрузка:** при приближении к переходу наверх — хук для этапа 5 (создать наблюдателя на уровне назначения).

3.7. Прототипы, спрайты-заглушки, `.ftl`.

**Где смотреть:** `SharedTransformSystem`, `PullingSystem`, `SharedBuckleSystem`, `SharedJointSystem`, `SharedDoAfterSystem`, `StepTriggerSystem`, `SharedEyeSystem`, примеры verbs; хелперы проверки занятости тайла (в SS14 они есть в `TurfSystem` — сверить).

**Подводные камни**
- Смена карты рвёт физические контакты — тело надо разбудить.
- Тянущий и тянутый на разных картах — рассинхрон и ошибки.
- Двойной перенос за один тик (сработали два триггера) — нужна защита.
- Клиент может ещё не иметь сущностей уровня назначения — после переноса они «подгружаются». Решается на этапе 5.

**Тесты:** стремянка вверх и вниз; ступени вверх и вниз; вход сбоку не срабатывает; заякоренная сущность не переносится; содержимое рюкзака переехало; тянутый — по правилу `DESIGN.md`; пристёгнутый отстёгнут; заблокированный выход — отказ.

**Ручная проверка:** два клиента. Игрок A поднимается, игрок B на верхнем уровне видит его появление. Нет зацикленного телепорта.

**Готово, когда:** тесты зелёные, переходы ощущаются нормально на клиенте, `PROGRESS.md` обновлён.

### Этап 4. Проёмы и падение

**Цель.** Дыра в полу, которая выглядит и работает как дыра: с неё падают на уровень ниже.

**Усилия:** high (предсказание падения — xhigh) · **Зависит от:** 3 · **Ветка:** `zlevels/stage-04-openspace`

**Задачи**

4.1. **Тайл `OpenSpace`** (`ContentTileDefinition`): не космос; прозрачный спрайт (или особый случай в отрисовке); держит атмосферу; на нём можно класть решётку и помост; разборка решётки над проёмом снова даёт `OpenSpace`.

4.2. **Разборка пола** на уровне, под которым есть уровень: в конце цепочки «пол → покрытие → решётка» получается `OpenSpace`, а не космос (через цепочку базовых тайлов или обработчик смены тайла — по `DESIGN.md`). На самом нижнем уровне — как раньше, космос.

4.3. **Триггер падения:** служебная сущность на каждом тайле `OpenSpace`, которая создаётся и удаляется автоматически при смене тайла. На ней `StepTrigger` — по образцу `ChasmSystem`. Альтернатива — проверка тайла в своей системе; выбрать по замеру. Эту же сущность использует атмос на этапе 8.

4.4. **Условия падения:** нет невесомости (`SharedGravitySystem.IsWeightless`); не летит (джетпак, летающие мобы, полёт); не пристёгнут; не заякорен; не в контейнере; на тайле нет «блокатора» (решётка, помост, закрытый люк — маркер `ZFallBlockerComponent` на прототипах).

4.5. **Само падение:** короткая анимация (спрайт быстро опускается); перенос вниз до первого «пола» (цепочка проёмов — несколько уровней, с пределом); урон по числу уровней (`DamageSpecifier` в прототипе); сбивание с ног или оглушение; звук. Приземление на моба — опционально урон обоим.

4.6. **Предметы:** брошенный или уроненный предмет падает после приземления.

4.7. **Валидация:** `OpenSpace` на самом нижнем уровне или над «ничем» — предупреждение (проверяется в тестах карт).

**Где смотреть:** `ChasmSystem`, `ChasmComponent`, `ChasmFallingComponent` (Chasm удаляет сущность, нам нужен перенос, но цепочка событий — `EntityStartFallingAttemptEvent` и другие — хороший образец), `StepTriggerSystem`, тайлы в `Resources/Prototypes/Tiles`, разборка тайлов, `SharedGravitySystem`, `DamageableSystem`, `SharedStunSystem`, `ThrowingSystem` и событие приземления.

**Подводные камни**
- Тысячи служебных сущностей в больших атриумах — замерить.
- Падение посреди переноса по ступеням.
- Падение тянутого или тянущего.
- Падение на `OpenSpace` нижнего уровня должно продолжаться, но конечно: предел глубины.

**Тесты:** падение на 1 и на 2 уровня с уроном; в невесомости не падает; помост блокирует; предмет падает; разборка пола даёт `OpenSpace` на верхнем уровне и космос на нижнем.

**Ручная проверка:** выломать пол на верхнем уровне, упасть, проверить урон и звук; включить и выключить гравитацию.

**Готово, когда:** тесты зелёные, падение выглядит прилично, `PROGRESS.md` обновлён.

**Промпт**
```text

Изучи ChasmSystem и StepTriggerSystem как образец. В режиме планирования предложи: тайл OpenSpace, служебную сущность проёма, условия и процесс падения, урон, предметы, тесты. ### Этап 5. Видимость соседних уровней: сеть и PVS

**Цель.** Клиент получает сущности уровня под собой (а при необходимости и над собой), чтобы их можно было нарисовать и чтобы переходы не сопровождались «подгрузкой».

**Усилия:** xhigh · **Зависит от:** 2 (лучше после 4) · **Ветка:** `zlevels/stage-05-pvs`

**Задачи**

5.1. Компонент наблюдателя на игроке (сервер): набор «глаз» по глубинам.

5.2. **Глаз** — невидимая, несохраняемая сущность без взаимодействий, с `EyeComponent`, на соседнем уровне в XY игрока. Подписка — `ViewSubscriberSystem.AddViewSubscriber(eye, session)`, снятие — `RemoveViewSubscriber`.

5.3. Позиция глаз обновляется по событию движения игрока или раз в тик для активных игроков (замерить, что дешевле).

5.4. **Жизненный цикл:** создание при входе в тело или в стек; пересоздание после переноса; удаление при отключении, смене тела, переходе в призрака (у призрака свои правила), удалении уровня.

5.5. **Политика:** ниже — когда в радиусе обзора есть проёмы (или всегда — по итогам пробы N); выше — при приближении к переходу наверх (предзагрузка) и при «посмотреть вверх».

5.6. **Ограничения:** для MVP — 1 уровень вниз и 1 вверх; радиус (если глаз позволяет масштабировать PVS — сверить); бюджеты PVS (CVars `net.pvs_*` — сверить имена).

5.7. Реестр стека виден клиентам (если не сделано на этапе 2).

**Где смотреть:** `SurveillanceCameraSystem` (там зрителя подписывают на камеру именно так), `ViewSubscriberSystem`, PVS-система движка и её CVars, события входа и выхода игрока из тела (сверить имена).

**Подводные камни**
- Лишний трафик: авторы KZLevels предупреждали держать 2–4 уровня.
- Утечки глаз.
- Глаз не должен попадать в поиск сущностей других систем (взрывы, поиск целей).

**Тесты:** сущность на уровне ниже рядом с игроком приходит клиенту, далёкая — нет; после отключения глаза удалены; после переноса — пересозданы.

**Ручная проверка:** замер трафика и нагрузки сервера с наблюдателями и без.

### Этап 8. Атмосфера между уровнями

**Цель.** Воздух, вакуум и огонь проходят через проёмы.

**Усилия:** max для дизайна, xhigh для реализации · **Зависит от:** 4, 7 · **Ветка:** `zlevels/stage-08-atmos`

**Задачи**

8.1. **Вертикальная связь:** тайл `OpenSpace` ↔ тайл под ним. MVP: служебная сущность проёма (из этапа 4) получает `AtmosDeviceComponent`. На каждом обновлении устройства она частично выравнивает смеси двух тайлов (доля зависит от перепада давления и шага времени) и «возбуждает» оба тайла, чтобы горизонтальный LINDA подхватил изменения.

8.2. **Граничные случаи:** под проёмом космос или нет грида — утечка в вакуум; стена или герметичный объект — обмена нет; ещё один проём — цепочка.

8.3. **Люк в полу:** герметичный, открывается и закрывается, с доступом. Закрыт — нет ни обмена газом, ни падения.

8.4. **Огонь:** горячая точка снизу поджигает тайл над проёмом; опционально «горячее поднимается».

8.5. Опционально: при сильном перепаде давления сущности у проёма затягивает вниз (через падение).

8.6. Замер стоимости: число связей, время атмос-тика.

8.7. **Полный 3D-атмос** (6 направлений) — опциональный этап B. Почему не сейчас: `AtmosDirection` знает только 4 стороны, массивы Monstermos рассчитаны на них, обработка идёт по гриду, а уровни — разные гриды.

**Где смотреть:** `AtmosphereSystem` (partial-файлы), `GridAtmosphereComponent`, `TileAtmosphere`, `AtmosDeviceComponent`, Airtight, горячие точки, методы получения смеси тайла и обмена газом.

**Подводные камни:** нестабильность (газ «скачет» между уровнями) при слишком большой доле обмена; порядок обработки гридов; стоимость при больших атриумах.

**Тесты:** давление выравнивается за N секунд; закрытый люк блокирует; разгерметизация нижнего уровня осушает верхний через проём; огонь переходит наверх.

**Готово, когда:** тесты зелёные, нет заметной просадки атмос-тика, `PROGRESS.md` обновлён.

```text

## 6. Опциональные этапы (после MVP)

| Этап | Что | Сложность и заметки |
|---|---|---|
| A | Многопалубные шаттлы | Очень высокая. Связанные гриды на разных картах: физика только у «ведущего», остальные повторяют его позицию и поворот каждый тик; FTL всем стеком; стыковка по уровням |
| B | Полный 3D-атмос | Высокая. Вертикальные соседи в `TileAtmosphere` между гридами разных карт, расширение направлений, Monstermos и возбуждённые группы через гриды. Только если MVP-обмен окажется недостаточным |
| C | Поддержка в движке | Высокая. Однопроходный рендер стека, PVS по стеку, интерполяция при смене уровня. Кандидат на PR в upstream (с учётом истории #7087) |
| D | Подземные и планетарные уровни | Средняя. Шахты под станцией, планета с пещерами (биомы), у планетарных карт карта сама является гридом |
| E | Лифты и грузовые подъёмники | Средняя. Перенос всех сущностей с платформы, анимация, двери шахты |
| F | Бой между уровнями | Средняя. Стрельба и броски сквозь проём, индикаторы игроков на соседних уровнях (идея из заметки на HackMD) |
| G | Высота внутри уровня | Высокая. Прыжки, «high ground», столы — как в закрытом PR движка (`ZLevelPhysicsSystem`, `ZLevelHighGroundComponent`) |

## 7. Риски и как их снижать

| Риск | Признак | Что делать |
|---|---|---|
| Рендер слишком дорогой | Проба R: большая просадка FPS | Глубина 1, пониженное разрешение, рендер только при проёмах в кадре; в крайнем случае патч Clyde (этап C) |
| Трафик PVS | Рост трафика и времени PVS на сервере | Наблюдатели только при проёмах и у переходов, малый радиус, 2–4 уровня |
| Конфликты при слияниях с upstream | Много конфликтов при обновлении форка | Код в папках ZLevels, маркеры в чужих файлах, маленькие правки |
| Лицензии | Код «похож» на CrystallEdge | Не открывать исходники CE в сессии; идеи — только из описаний; при желании портировать — письменное разрешение |
| Рывки при переходах | Телепорт заметен на клиенте | Серверный перенос + анимация; предсказание — позже |
| Нестабильный атмос | Газ «скачет», просадка атмос-тика | Меньшая доля обмена, ограничение частоты, тесты стабильности |
| Аудит «одного места» неполный | Странные баги «работает только на основной палубе» | Регулярно повторять поиск по паттернам приложения В; тест-раунды на тестовой карте |
| Claude теряет контекст | Повторные исследования, противоречивые решения | Записки в `notes/`, `PROGRESS.md`, `DECISIONS.md`, вложенные `CLAUDE.md`, новая сессия на этап |
| Ошибки сохранения карт | Уровни «съезжают», теряются компоненты | Тест «сохранить → загрузить», валидация выравнивания |
| Движок обновился в upstream | Сломались API после обновления подмодуля | Обновлять движок отдельной задачей, между этапами, с полным прогоном тестов |

## Приложение В. Паттерны поиска для аудита «одного места»

Искать по `Content.Server`, `Content.Shared`, `Content.Client` (движок — только для понимания):

| Паттерн | Что ищем |
|---|---|
| `MapID ==`, `MapID !=`, `MapId ==`, `MapId !=` | Сравнения карт |
| `MapUid ==`, `MapUid !=`, `GetMapId(` | Сравнения сущностей карт |
| `GridUid ==`, `GridUid !=` | «Тот же грид» (как в проводной сети устройств) |
| `ParentUid` рядом с `GravityComponent` или гридом | Логика «мой грид» (как у генератора гравитации) |
| `GetOwningStation`, `StationDataComponent`, `GetLargestGrid` | Станционная принадлежность |
| `AddInMap`, `BroadcastMap`, `AddInGrid` (фильтры получателей) | Рассылки по карте или гриду |
| `HasActiveServer`, `LongRange`, `GlobalReceive` | Радио |
| `InRangeUnobstructed`, `GetEntitiesInRange` | Где межкартовость отсекается само (обычно это правильно) |
| `IsWeightless` | Невесомость: падать или нет |
| `IEyeManager` и `CurrentMap`/`CurrentEye` в клиентских оверлеях | Оверлеи, которые сломаются на дополнительном вьюпорте |

Для каждого найденного места — строка в `notes/mapid-audit.md`: `файл:строка | что проверяет | «как одна карта» / «как разные» / «не важно» | MVP / позже`.
